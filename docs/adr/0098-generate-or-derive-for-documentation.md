# ADR 0098: Generate or derive — the rule for documentation that restates the code

## Status

Accepted (2026-08-25)

## Context

Epic #475 exists because this repository kept writing the same fact down twice and
then guarding the copy with a test that could not tell a current copy from a stale
one. Three shapes of that recurred:

- **A hand-maintained mirror.** `README.md` carried 126 rows naming MCP tools. The
  registry held 148. 31 registered tools had no row; nine rows named tools deleted
  under ADR 0055 and ADR 0076. ADR 0097 replaced the table with `docs/tools/`,
  generated from `TOOL_SECURITY`.
- **A presence assertion standing in for a content check.**
  `tests/test_ci_pipeline.py` asserts that recipe names and literal command strings
  appear in `justfile` and `ci.yml`. A recipe renamed in both files passes. A recipe
  whose body was replaced by `true` passes. The test states that a name is written
  somewhere, which is not the property anyone wanted.
- **A count kept in step by memory.**
  `test_prek_hooks_delegate_to_focused_just_recipes` pins
  `config.count("pass_filenames: false") == 8` — a number in a test that must be
  edited by hand every time a hook is added, in a file about something else.

ADR 0097 fixed one surface. It says nothing about the next one. Without a recorded
rule and something enforcing it, the next generated surface arrives with no
freshness gate, or `docs/tools/` is deleted and hand-written back, and the epic's
starting state returns.

#480 also recorded two designs that were proposed and rejected, so they are not
re-proposed:

**A registry of guards** — an `@enforces("<property>")` decorator on each guard plus
a meta-test demanding a paired negative control. Rejected: the property string is
written by the same hand, in the same edit, as the guard it describes. That is the
epic's own defect relocated, not removed.

**Asserting that each banner-carrying document "has a freshness recipe wired into
CI"** — rejected as the presence defect in a new hat. It checks that a recipe is
*wired*, not that it *works*; a recipe whose body is `true` satisfies it; and it
quantifies over banner-carrying documents, so deleting the last one makes it
vacuously green.

## Decision

### 1. The rule

Every document in this repository falls into exactly one of three classes, and the
class determines what guards it.

**1a. A document that restates a derivable fact is generated, not written.** If the
fact has a machine-readable source of truth in the tree — the tool registry, the
config model's fields, a workflow matrix — the document is produced from that source
by a script, committed, and verified by regenerating it and diffing. The generated
copy carries a banner (§2) naming both its generator and the command that
regenerates it.

**1b. A document that carries judgement keeps its prose, and its embedded facts are
checked individually.** Narrative documentation — `README.md`, `CONTRIBUTING.md`,
`docs/environment-variables.md`, these records — exists to say *why*, and generating
it would destroy the thing it is for. Where such a document embeds a derivable fact,
a content check asserts that fact against its source without touching the prose.
`scripts/check_env_vars.py` (every `HMC_*` field of `HMCConfig` is documented) and
`scripts/check_nicknames.py` (the committed fixture's nicknames table is
well-formed) are this class. They are **not** generated-document checks and this
ADR's walker does not reach them; §3 quantifies over banners, and these documents
correctly carry none.

**1c. A guard that asserts presence is a defect.** A test that asserts a name, a
literal string, or a count appears in a file states that something was written, not
that it is correct. Where the underlying property is derivable, the guard must
derive and compare it. Where it is not derivable, the guard must be honest about
what it covers rather than dressing presence up as enforcement.

### 2. The banner is the contract

A generated document declares itself, on its first line, in exactly this shape:

```
<!-- Generated by <script path>; do not edit. Regenerate: just <name>-docs -->
```

`docs/tools/*.md` already carry it:

```
<!-- Generated by scripts/gen_tool_reference.py; do not edit. Regenerate: just tool-docs -->
```

Two properties follow from the banner being machine-readable rather than prose.
First, a reader who lands on a generated page from a search result learns not to
edit it and learns what to run instead. Second — the load-bearing one — the set of
generated documents and the command that rebuilds each of them are **derived from
the tree**, so nothing has to be remembered when a surface is added. The banner is
the whole registration for a document the walk can reach, which §2a bounds.

The command must be `just <name>-docs`. Naming the recipe rather than the script
keeps one invocation of the generator in the repository, which is what `CLAUDE.md`
asks of hooks and CI: the recipe is the single source of truth and only its
invocation is duplicated. The `-docs` suffix is required, not conventional, and for
two reasons. The guard *executes* what the banner names, so a banner that could say
`Regenerate: just setup` would be a file's first line choosing what runs against the
developer's own environment. And it makes §3's orphan clause the exact inverse of
the banner: the same set of recipe names on both sides.

### 2a. What the banner can register

A `*.md` file under `docs/`. That is the walk, and it bounds every claim below.

A banner on a Markdown file **outside** `docs/` is reported as an error rather than
ignored, so the boundary announces itself instead of swallowing a document. A
generated surface that is not Markdown — a JSON index, a rendered HTML page — cannot
carry a banner at all and is out of scope; adding one would mean giving this guard a
per-format comment syntax, and there is no such surface today. Extending the walk is
the change to make when one arrives, and until then §4 lists this among what is not
covered rather than leaving it implied.

### 3. One check, executing rather than inspecting

`scripts/check_generated_docs.py` (`just doc-freshness`) reads the first line of
every Markdown file in the tree, collects the banners, and for each distinct
regeneration command:

1. copies the working tree into a temporary directory **without the top-level
   `docs/`**, symlinking `.venv` rather than copying it;
2. runs the command there;
3. compares what it produced against what is committed.

Executing is the point. A recipe whose body is `true` produces nothing, so every
document claiming that command is reported as un-produced and the check reddens.
That is a content check on the regeneration path itself, which no amount of
inspecting `ci.yml` can be.

The temp tree starts with **no `docs/`** deliberately. Copying the committed
documents in first would let a no-op command pass by leaving them untouched — the
same vacuity in a different place.

Six failures, in both directions:

- **Stale or missing output.** A committed document whose banner names command *C*
  that *C* did not produce, or produced with different bytes.
- **Uncommitted output.** A file *C* produced that is not committed, or is committed
  with different bytes.
- **Unbannered output.** A file *C* produced that does not carry a banner naming
  *C*. Without this, a generator that grows a new page and forgets the banner adds
  an unwalked document — the walker's own coverage hole — and the hole would be
  invisible to the walker.
- **Dangling banner.** A banner naming a recipe the justfile does not define.
- **Orphaned recipe.** A recipe named `*-docs` that no banner names. This is the
  deletion catch: remove `docs/tools/` and the `tool-docs` recipe is orphaned.
- **Misplaced banner.** A banner on a Markdown file outside `docs/` (§2a).

And one non-vacuity condition: **finding no banner at all is a failure.** A
universal claim over an empty set is true and worthless. Delete the *last* generated
surface, hand-write a replacement without a banner, and the walk comes up empty —
which reddens rather than passing. The word *last* is load-bearing and §4 says so.

### 4. What this does not catch, stated plainly

This ADR does not claim that documentation cannot drift. It claims three specific
things, and the rest is a reviewer's job.

**Mechanically enforced:**

- A committed generated document cannot differ from what its declared command
  produces (§3).
- A declared regeneration command cannot be absent, unrunnable, or a no-op (§3).
- A `*-docs` recipe cannot exist with nothing generated by it, and a banner cannot
  name a recipe that is gone (§3).
- The walk cannot be vacuously green — that is, it cannot come up empty (§3).

**A review obligation, not a mechanical guarantee:**

- **A newly hand-written mirror with no banner is invisible to this check.** Someone
  who adds `docs/tools-summary.md` restating the registry in prose, with no banner
  and no recipe, defeats every clause above — the walker quantifies over banners and
  this document has none. Nothing mechanical can catch it, because deciding that a
  paragraph restates a derivable fact is the judgement §1 asks a reviewer to make.
  It is a review obligation and this record does not pretend otherwise.
- **Deleting one surface out of several is not caught once a second surface
  exists.** Remove `docs/api/`, remove its `api-docs` recipe, and hand-write
  `docs/api.md` in their place: the orphan clause needs the recipe to survive, and
  the non-vacuity condition needs `docs/tools/` to have gone too. What §3 catches is
  removing the *arrangement*, not removing *a* surface from it. This limit does not
  bite today — there is one surface, so deleting it is deleting the last one — and
  it starts biting on the day the second one lands, which is the day this record
  exists for. A mechanical catch would need a generated manifest that itself carries
  a banner, so that removing a surface changes committed bytes; that is a real
  design and is deliberately not built for a set of one. Until then, deleting a
  generated surface is a reviewer's call.
- **The `*-docs` naming convention in §3's orphan clause is a convention, not a
  derivation.** A regeneration recipe named `gen-api` rather than `api-docs` is not
  checked for orphanhood, and its banner would be rejected by §2's grammar rather
  than accepted, so the convention has to be followed to opt in at all. The other
  clauses reach a surface the moment a conforming banner names it; only the deletion
  catch depends on the name.
- **A generated surface outside `docs/`, or in a format that cannot carry a Markdown
  comment, is out of the walk (§2a).** A banner outside `docs/` is at least
  reported; a generated `.json` cannot register at all and its `*-docs` recipe would
  be reported as orphaned forever. Nothing here covers such a surface, and adding
  one means extending the walk in the same change.
- **A generator that renders the wrong thing correctly is invisible.** Both sides of
  §3's comparison come from the same generator, so the diff proves the copy is
  current, never that it is right. The generator's own tests carry that weight (ADR
  0097).
- **Choosing class 1a over 1b for a new document is a judgement call.** The rule says
  which guard follows from the class; it cannot compute the class.

This is the same correction ADR 0092 §5 received during the campaign that produced
this epic: its "coverage cannot silently regress" claim was stronger than any test
could deliver and had to be rewritten to say which half is mechanical and which is a
reviewer's. Stating the boundary is the point of the record.

### 5. A regeneration command must not read the tree it writes

§3 runs each command against a copy with the top-level `docs/` removed. A generator
that reads one document to produce another would see an empty tree and fail there
while passing locally. Generators take their input from the source of truth — code,
schema, configuration — never from another document. This falls out of §1a rather
than being an extra rule: a generator reading a document is deriving from a copy.

Only the top-level `docs/` is withheld. A directory named `docs` nested anywhere
else is ordinary content and is copied, so a generator whose *source* happens to sit
in one is unaffected.

### 6. Wiring

`just doc-freshness` joins `static`, gets a prek hook like every other `static`
member, and is named as its own CI step as well as reached through `static` ->
`verify` — the pattern ADR 0097 adopted, so drift is its own failed check with its
own name rather than one line inside a twenty-minute umbrella run.

`just tool-docs-check` stays. It is not the same job: it owns `docs/tools/` as a
**wholly generated directory** and rejects any file there the generator did not
write, including a hand-written one with no banner. The walker cannot make that
claim generically — it has no way to know which directories are wholly generated —
so the two guards cover different failures, and the one narrower guard is where the
one hand-written-mirror hole is actually closed for the one surface that has one.

## Consequences

- Adding a generated surface requires the banner and a `*-docs` recipe. Nothing else
  is registered, listed, or remembered; the check finds it on the next run. This is
  stronger than the per-surface `*-docs-check` recipe arrangement it grows out of,
  where each new surface had to be wired into CI by hand.
- **The walker currently quantifies over one document set.** `docs/tools/` is the
  only banner-carrying surface in the repository, so §3's universal claims range
  over 35 files produced by one command. #480 flagged this as the weakness of the
  rejected design and it is equally true here: the freshness half is, today, a
  second gate on a surface that already had one. What is *not* one-element is the
  bidirectional half — the orphan and dangling clauses and the non-vacuity condition
  constrain the justfile and the whole of `docs/`, and they are what stops the
  arrangement from being deleted. The value of the freshness half is that it costs
  nothing to add the second surface.
- The check runs the generator, so the application gets composed more often. `just
  doc-freshness` measures at 1.7s against `tool-docs-check`'s 1.6s, and a CI leg
  reaches the walker three times — its own step, `verify` -> `static`, and `prek run
  --all-files` — plus a fourth inside the suite, where
  `test_passes_on_the_committed_repository` runs the whole thing end to end. Call it
  seven seconds added to each of eight legs. It is the price of executing rather
  than inspecting, and inspecting is what #480 rejected.
- **The unit suite now depends on `just` and a populated `.venv`.** The end-to-end
  test runs the real regeneration command, which is what makes it end-to-end; it is
  not a test that can be run from a bare checkout. `just setup` is the prerequisite
  it shares with every other recipe in the repository.
- The check needs `just`, `uv` and a populated `.venv` at the point it runs. It runs
  after `just setup` in CI and inside a prek hook locally, so all three are present;
  a bare `python scripts/check_generated_docs.py` in an unprepared checkout will
  fail on the subprocess rather than pass vacuously.
- **This ADR does not subsume #510.** Decision records are class 1b — they are
  judgement, not generated — so they carry no banner and the walker does not reach
  them. #510's property (a record's H1 number must match its filename number) is a
  content check on a prose document and belongs in
  `scripts/check_adr_numbering.py`, which is exactly where §1b says it goes.
- The presence assertions in `tests/test_ci_pipeline.py` are now, by §1c, recorded
  defects rather than accepted practice. Epic #475 owns replacing the rest of them.
  One went in the same change as this rule, because adding a `static` member would
  otherwise have meant hand-editing `config.count("pass_filenames: false") == 8` in a
  test about something else: `test_prek_hooks_delegate_to_focused_just_recipes` now
  parses `static`'s dependency list and the hook file's `entry: just <recipe>` lines
  and asserts the two are the same set, with the count derived from the hooks it
  found. Neither list is written down twice any more, and the property the test
  states — one hook per `static` member — is the one that was wanted.

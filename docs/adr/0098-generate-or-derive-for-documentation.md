# ADR 0098: Generate or derive — the rule for documentation that restates the code

## Status

Accepted (2026-08-25)

## Context

Epic #475 exists because this repository kept writing the same fact down twice and
then guarding the copy with a test that could not tell a current copy from a stale
one. Three shapes of that recurred:

- **A hand-maintained mirror.** `README.md` carried 126 rows naming MCP tools. The
  registry held 148. 31 registered tools had no row; nine rows named tools deleted
  under ADR 0055 and ADR 0076. ADR 0097 replaced the table with `docs/tools/`,
  generated from `TOOL_SECURITY`.
- **A presence assertion standing in for a content check.**
  `tests/test_ci_pipeline.py` asserts that recipe names and literal command strings
  appear in `justfile` and `ci.yml`. A recipe renamed in both files passes. A recipe
  whose body was replaced by `true` passes. The test states that a name is written
  somewhere, which is not the property anyone wanted.
- **A count kept in step by memory.**
  `test_prek_hooks_delegate_to_focused_just_recipes` pins
  `config.count("pass_filenames: false") == 8` — a number in a test that must be
  edited by hand every time a hook is added, in a file about something else.

ADR 0097 fixed one surface. It says nothing about the next one. Without a recorded
rule and something enforcing it, the next generated surface arrives with no
freshness gate, or `docs/tools/` is deleted and hand-written back, and the epic's
starting state returns.

#480 also recorded two designs that were proposed and rejected, so they are not
re-proposed:

**A registry of guards** — an `@enforces("<property>")` decorator on each guard plus
a meta-test demanding a paired negative control. Rejected: the property string is
written by the same hand, in the same edit, as the guard it describes. That is the
epic's own defect relocated, not removed.

**Asserting that each banner-carrying document "has a freshness recipe wired into
CI"** — rejected as the presence defect in a new hat. It checks that a recipe is
*wired*, not that it *works*; a recipe whose body is `true` satisfies it; and it
quantifies over banner-carrying documents, so deleting the last one makes it
vacuously green.

## Decision

### 1. The rule

Every document in this repository falls into exactly one of three classes, and the
class determines what guards it.

**1a. A document that restates a derivable fact is generated, not written.** If the
fact has a machine-readable source of truth in the tree — the tool registry, the
config model's fields, a workflow matrix — the document is produced from that source
by a script, committed, and verified by regenerating it and diffing. The generated
copy carries a banner (§2) naming both its generator and the command that
regenerates it.

**1b. A document that carries judgement keeps its prose, and its embedded facts are
checked individually.** Narrative documentation — `README.md`, `CONTRIBUTING.md`,
`docs/environment-variables.md`, these records — exists to say *why*, and generating
it would destroy the thing it is for. Where such a document embeds a derivable fact,
a content check asserts that fact against its source without touching the prose.
`scripts/check_env_vars.py` (every `HMC_*` field of `HMCConfig` is documented) and
`scripts/check_nicknames.py` (the committed fixture's nicknames table is
well-formed) are this class. They are **not** generated-document checks and this
ADR's walker does not reach them; §3 quantifies over banners, and these documents
correctly carry none.

**1c. A guard that asserts presence is a defect.** A test that asserts a name, a
literal string, or a count appears in a file states that something was written, not
that it is correct. Where the underlying property is derivable, the guard must
derive and compare it. Where it is not derivable, the guard must be honest about
what it covers rather than dressing presence up as enforcement.

### 2. The banner is the contract

A generated document declares itself, on its first line, in exactly this shape:

```
<!-- Generated by <script path>; do not edit. Regenerate: just <name>-docs -->
```

`docs/tools/*.md` already carry it:

```
<!-- Generated by scripts/gen_tool_reference.py; do not edit. Regenerate: just tool-docs -->
```

Two properties follow from the banner being machine-readable rather than prose.
First, a reader who lands on a generated page from a search result learns not to
edit it and learns what to run instead. Second — the load-bearing one — the set of
generated documents and the command that rebuilds each of them are **derived from
the tree**, so nothing has to be remembered when a surface is added. The banner is
the whole registration for a document the walk can reach, which §2a bounds.

The command must be `just <name>-docs`. Naming the recipe rather than the script
keeps one invocation of the generator in the repository, which is what `CLAUDE.md`
asks of hooks and CI: the recipe is the single source of truth and only its
invocation is duplicated. The `-docs` suffix is required, not conventional, and for
two reasons. The guard *executes* what the banner names, so a banner that could say
`Regenerate: just setup` would be a file's first line choosing what runs against the
developer's own environment. And it makes §3's orphan clause the exact inverse of
the banner: the same set of recipe names on both sides.

Name the recipe, not an alias for one: recipe names come from `just --summary`, which
does not list aliases, so a banner naming an alias is reported as dangling. That fails
closed and the message says which name it could not find.

### 2a. What the banner can register

A **tracked** `*.md` file under `docs/`. That is what a banner can register, and it
bounds every claim below. The walk itself is every tracked `*.md` file, because the
near-miss clause has to reach a broken banner wherever someone wrote it; registration
is the narrower thing.

*Tracked* means `git ls-files`, not a directory listing, and the difference runs both
ways. A page the generator wrote at a path nobody staged is absent from what CI will
check out, so it is reported rather than quietly making the local run agree with
itself. An ignored or vendored document — `docs/refs/` here holds hundreds of
third-party pages — is not the repository's to answer for, and reddening `just
static` for a file that is not in the repository would be a gate with no CI
reproduction and no way to silence it. It also means the guard needs no
hand-maintained mirror of `.gitignore` to know what to skip, which would have been
this record's own defect inside its own enforcement.

**Paths come from the index; bytes come from the working tree.** The guard checks
that the tree in front of you is self-consistent — the documents it holds are what
its code produces — not that the tree matches any commit. It has to: the regeneration
command runs against the working tree's source, so comparing its output to committed
bytes would report every in-progress edit as stale. The consequence is that
*modified-but-unstaged* generated content passes here and reddens on a fresh
checkout. `git add` is what closes that, and CI is what catches it not having
happened; §4 says so rather than claiming otherwise.


A banner on a Markdown file **outside** `docs/` is reported as an error rather than
ignored, so the boundary announces itself instead of swallowing a document. A
generated surface that is not Markdown — a JSON index, a rendered HTML page — cannot
carry a banner at all and is out of scope; adding one would mean giving this guard a
per-format comment syntax, and there is no such surface today. Extending the walk is
the change to make when one arrives, and until then §4 lists this among what is not
covered rather than leaving it implied.

**The `*-docs` suffix is a safety boundary, not only a name.** §2 requires the suffix so
the grammar cannot admit `Regenerate: just setup`. The guard executes what a banner names
and a banner is a file's first line, so that requirement is what stands between a tracked
Markdown file and the command it causes to run — but read exactly what it bounds, which is
the recipe a banner may *name*, and nothing past it. `just` runs a recipe's dependencies,
so `api-docs: setup` puts `setup` one banner away again, and every clause here is blind to
it: the grammar and the orphan clause test names, and §3 tests produced bytes. The
obligations below therefore bind everything a `*-docs` recipe reaches — its dependency
list and its body, transitively — and not merely the recipe carrying the name.

The one narrowing runs the other way and fails closed. Recipe names come from `just
--summary`, which does not list `[private]` recipes, so a private `*-docs` recipe is not
admitted at all and a banner naming it is reported as dangling (§2).

Naming a recipe `*-docs` is what first makes something executable by anyone who can land a
Markdown file here, so the name is where the decision is most visible. It is not where the
decision is closed: adding a dependency to an existing `*-docs` recipe widens what its
banner reaches, with no rename and no new banner. Two obligations follow.

**A recipe matching `*-docs` must be side-effect-free and deterministic.** Its whole
effect must be the generated documents under its working directory's `docs/`: no publish,
no upload, no deploy, no push, no external service, no credentialed call, no write that
outlives the run. And its output must be a function of the tracked source alone — the same
tree must produce the same bytes every time — because §3 compares what the command
produces against the tracked page in the working tree, and a page stamped with a time, a
hostname, or an unordered mapping reddens all eight legs against a tree nobody edited.

Determinism is the word §3 earns, and idempotence falls out of the first obligation rather
than standing beside it: a recipe that produces nothing but its own `docs/` leaves no
residue for a second run to meet. What §3 exercises is repetition from identical state —
each walker run gets a fresh temporary directory and a fresh copy of the tracked tree, and
runs the command once — so the property it can catch is a page whose bytes vary between
runs. §4's "re-runs to the same bytes" is that property under its own name.

Read that as an obligation on the recipe and not as a claim about the scratch tree,
because §3's copy is not a write boundary. It symlinks `.venv`, and this project is
installed editable, so `.venv/` and anything reached through `import hmc_mcp` resolve to
the real checkout — the asymmetry §5 records for reading, in the writing direction. A
recipe writing through either one writes into the developer's own tree, on every prek
hook and every `just static`, and nothing stops it. So *writes only inside the tree it
runs in* is the wrong test to hand a reviewer; *produces nothing but its own `docs/`* is
the right one. A recipe that acts outside that is not a documentation generator and does
not belong under this suffix — but renaming it `publish-documentation` removes it from the
banner grammar only, not from a `*-docs` recipe's dependency list, so the rename is
bookkeeping and the obligation is what does the work.

**A recipe matching `*-docs` must not read a secret.** Every gate that compares generated
bytes quotes them into CI logs, and the likelier path does not involve failing. On a
non-zero exit §3 folds the command's captured stdout and stderr into the message it
prints. On a *successful* run whose output differs from what is tracked, §3 prints a
unified diff of the generated bytes themselves — so a generator that writes a credential
into a page it produces discloses it on the first run, through the ordinary staleness
path, with nothing exceptional involved. And §3 is not the only such gate: a per-surface
`*-docs-check` recipe prints the same diff from the generator itself
(`scripts/gen_tool_reference.py --check`), reached through `static` and through its own
prek hook, and §6 keeps that arrangement — so every future surface adds another. GitHub
masks the secrets it has been given and nothing masks the rest.

Bounding the quoted output is not the control. §3 caps how many differing files get a full
diff — `_MAX_DIFFS` keeps three whole diffs and only names the rest — and quotes a failed
command's output whole, because that output is what makes a failed generator diagnosable.
Neither is a disclosure bound, and the first is not even a size bound: a retained page goes
in at whatever length it is, and a credential inside any retained page, or any retained
prefix, reaches the log. What a generator may read is the control. Today's generator reads
the tool registry and no credential; this is a constraint on the next one.

`publish-docs`, `upload-docs`, and `deploy-docs` are all natural names for recipes that
would break these obligations, and the person choosing one is editing `justfile` rather
than `scripts/check_generated_docs.py`. §4 records that nothing checks any of this, and
where the constraint is and is not written down.

### 3. One check, executing rather than inspecting

`scripts/check_generated_docs.py` (`just doc-freshness`) reads the first line of
every tracked Markdown file (§2a), collects the banners, and for each distinct
regeneration command:

1. copies the tracked files into a temporary directory **without the top-level
   `docs/`**, symlinking `.venv` rather than copying it;
2. runs the command there;
3. compares what it produced against what is committed.

Executing is the point. A recipe whose body is `true` produces nothing, so every
document claiming that command is reported as un-produced and the check reddens.
That is a content check on the regeneration path itself, which no amount of
inspecting `ci.yml` can be.

The temp tree starts with **no `docs/`** deliberately. Copying the committed
documents in first would let a no-op command pass by leaving them untouched — the
same vacuity in a different place.

Seven failures, in both directions:

- **Stale or missing output.** A tracked document whose banner names command *C*
  that *C* did not produce, or produced with different bytes.
- **Untracked output.** A file *C* produced that git does not track — or tracks and
  the working tree no longer has, which gets its own message because `git rm` and
  regeneration are different remedies.
- **Near-miss banner.** A tracked Markdown file whose first line opens an HTML
  comment and mentions generation but does not match the grammar. Without this a
  typo would remove a document from the walked set instead of reporting anything,
  which is failure-by-silence in the one place this record cannot afford it.
- **Unbannered output.** A file *C* produced that does not carry a banner naming
  *C*. Without this, a generator that grows a new page and forgets the banner adds
  an unwalked document — the walker's own coverage hole — and the hole would be
  invisible to the walker.
- **Dangling banner.** A banner naming a recipe the justfile does not define.
- **Orphaned recipe.** A recipe named `*-docs` that no banner names. This is the
  deletion catch: remove `docs/tools/` and the `tool-docs` recipe is orphaned.
- **Misplaced banner.** A banner on a Markdown file outside `docs/` (§2a).

And one non-vacuity condition: **finding no banner at all is a failure.** A
universal claim over an empty set is true and worthless. Delete the *last* generated
surface, hand-write a replacement without a banner, and the walk comes up empty —
which reddens rather than passing. The word *last* is load-bearing and §4 says so.

### 4. What this does not catch, stated plainly

This ADR does not claim that documentation cannot drift. It claims the five things
below, and the rest is a reviewer's job.

**Mechanically enforced:**

- A **tracked** generated document, as the working tree holds it, cannot differ from
  what its declared command produces (§3). Bytes changed and not staged are outside
  this: the guard checks the tree you are in, and CI checks the commit (§2a).
- A declared regeneration command cannot be absent, unrunnable, or a no-op (§3).
- A `*-docs` recipe cannot exist with nothing generated by it, and a banner cannot
  name a recipe that is gone (§3).
- The walk cannot be vacuously green — that is, it cannot come up empty (§3).
- A generated page written at a path nobody staged cannot pass: the walk is
  `git ls-files` (§2a).

**A review obligation, not a mechanical guarantee:**

- **A newly hand-written mirror with no banner is invisible to this check.** Someone
  who adds `docs/tools-summary.md` restating the registry in prose, with no banner
  and no recipe, defeats every clause above — the walker quantifies over banners and
  this document has none. Nothing mechanical can catch it, because deciding that a
  paragraph restates a derivable fact is the judgement §1 asks a reviewer to make.
  It is a review obligation and this record does not pretend otherwise.
- **Deleting one surface out of several is not caught once a second surface
  exists.** Remove `docs/api/`, remove its `api-docs` recipe, and hand-write
  `docs/api.md` in their place: the orphan clause needs the recipe to survive, and
  the non-vacuity condition needs `docs/tools/` to have gone too. What §3 catches is
  removing the *arrangement*, not removing *a* surface from it. This limit does not
  bite today — there is one surface, so deleting it is deleting the last one — and
  it starts biting on the day the second one lands, which is the day this record
  exists for. A mechanical catch would need a generated manifest that itself carries
  a banner, so that removing a surface changes committed bytes; that is a real
  design and is deliberately not built for a set of one. Until then, deleting a
  generated surface is a reviewer's call.
- **The `*-docs` naming convention in §3's orphan clause is a convention, not a
  derivation.** A regeneration recipe named `gen-api` rather than `api-docs` is not
  checked for orphanhood, and its banner would be rejected by §2's grammar rather
  than accepted, so the convention has to be followed to opt in at all. The other
  clauses reach a surface the moment a conforming banner names it; only the deletion
  catch depends on the name.
- **Nothing checks that a recipe named `*-docs` is safe to run (§2a).** The orphan
  clause makes a new one *visible* — add `publish-docs` and `just doc-freshness` reddens
  until a banner names it — but visibility is not safety, and the banner that clears the
  orphan clause is the same act that makes the recipe reachable from any Markdown file.
  What would have to be checked is that a recipe — and everything its dependency list and
  body reach — produces nothing but its own `docs/` and reads no credential. Both are
  properties of arbitrary shell and of every program it invokes, and §5's scratch tree
  isolates the working directory rather than the process — and not even that, since it
  symlinks `.venv` — so the guard has no sandbox to measure them against. The third
  property §2a asks for, that the output be a function of the tracked source alone, is the
  one §3 does enforce and enforces for free: a page whose bytes vary between runs cannot
  match its tracked copy, so it reddens on the first run rather than needing a doubled one.
  So the suffix's safety half is a reviewer's, and the review to do falls when a recipe is
  named — and again on any edit to a `*-docs` recipe's dependency list or body, which
  widens what an existing banner reaches while every clause here stays green.
  That review is detective rather than preventive, and §4 should not imply otherwise: one
  change can add the recipe and the banner together, CI runs the walker on
  `pull_request`, and a contributor's prek hook runs it locally, so the recipe's first
  execution precedes anyone reading its name. What the review buys is stopping the second
  one — and only where recipe edits are being read as security-relevant at all, which a
  one-word dependency added to an existing `*-docs` recipe does not look like. Nor is the obligation written where the recipe is named: it is recorded in
  §2a and at `_RECIPE`, which is where #524 judged an author most likely to meet it, while
  `justfile` — the file that author actually edits — carries no note. That omission is
  deliberate, and it is §1's own argument turned on this record: a third hand-maintained
  copy of a prose constraint, with nothing deriving one from another, is one more copy to
  drift. Someone who decides the duplication is worth its drift can add the line; until
  then this is where the obligation lives, and this bullet is why it is a review
  obligation rather than something an author trips over.
- **A generated surface outside `docs/`, or in a format that cannot carry a Markdown
  comment, is out of the walk (§2a).** A banner outside `docs/` is at least
  reported; a generated `.json` cannot register at all and its `*-docs` recipe would
  be reported as orphaned forever. Nothing here covers such a surface, and adding
  one means extending the walk in the same change.
- **The scratch tree withholds `docs/`, not every document, and isolates the working
  directory, not `sys.path` (§5).** A generator that reads documentation outside
  `docs/`, or reaches the tree through the installed package rather than through a
  relative path, reads the real files and a document-to-document copy would pass.
  Whether a generator derives from the source of truth or from another document is
  read off the generator, by a reviewer.
- **A generated document modified but not staged passes here and reddens in CI
  (§2a).** The guard compares working-tree bytes, because the command it runs reads
  working-tree source; `git add` is the step that makes the two agree.
- **A generator that renders the wrong thing correctly is invisible.** Both sides of
  §3's comparison come from the same generator, so the diff proves the copy is
  current, never that it is right. The generator's own tests carry that weight (ADR
  0097).
- **Choosing class 1a over 1b for a new document is a judgement call.** The rule says
  which guard follows from the class; it cannot compute the class.

This is the same correction ADR 0092 §5 received during the campaign that produced
this epic: its "coverage cannot silently regress" claim was stronger than any test
could deliver and had to be rewritten to say which half is mechanical and which is a
reviewer's. Stating the boundary is the point of the record.

### 5. A regeneration command must not read the tree it writes

Generators take their input from the source of truth — code, schema, configuration —
never from another document. This falls out of §1a rather than being an extra rule: a
generator reading a document is deriving from a copy.

§3's scratch tree gives that rule partial teeth and no more, and the boundary matters
enough to state exactly. The copy withholds the top-level `docs/`, so a generator
that reads a document **under `docs/`, through a path relative to its working
directory,** finds nothing there and fails. Every other tracked file is copied, so a
generator reading `README.md` — or a mirror parked outside `docs/` — succeeds and the
guard is satisfied. And `.venv` is symlinked rather than rebuilt, and this
project is installed editable, so `import hmc_mcp` resolves to the real checkout: a
generator that reaches documentation **through the installed package** — from
`Path(hmc_mcp.__file__).parents[2] / "docs"` — reads the real `docs/` and the guard
is satisfied. Rebuilding the environment inside the scratch tree would close that,
at the cost of a `uv sync` on every run of every gate. It is not worth that, so §4
lists it as a review obligation instead of a claim.

Only the top-level `docs/` is withheld. A directory named `docs` nested anywhere
else is ordinary content and is copied, so a generator whose *source* happens to sit
in one is unaffected.

### 6. Wiring

`just doc-freshness` joins `static`, gets a prek hook like every other `static`
member, and is named as its own CI step as well as reached through `static` ->
`verify` — the pattern ADR 0097 adopted, so drift is its own failed check with its
own name rather than one line inside a twenty-minute umbrella run.

`just tool-docs-check` stays. It is not the same job: it owns `docs/tools/` as a
**wholly generated directory** and rejects any top-level `*.md` file there the
generator did not write, including a hand-written one with no banner. The walker
cannot make that claim generically — it has no way to know which directories are
wholly generated — so the two guards cover different failures, and the narrower one
is where the hand-written-mirror hole is closed for the one surface that has a guard
able to close it. Its `output.glob("*.md")` is not recursive, so
`docs/tools/sub/mirror.md` escapes both guards; that is §4's hand-written-mirror
obligation again, in the place it is least expected.

## Consequences

- Adding a generated surface requires the banner and a `*-docs` recipe. Nothing else
  is registered, listed, or remembered; the check finds it on the next run. This is
  stronger than the per-surface `*-docs-check` recipe arrangement it grows out of,
  where each new surface had to be wired into CI by hand.
- **The walker currently quantifies over one document set.** `docs/tools/` is the
  only banner-carrying surface in the repository, so §3's universal claims range
  over 35 files produced by one command. #480 flagged this as the weakness of the
  rejected design and it is equally true here: the freshness half is, today, a
  second gate on a surface that already had one. What is *not* one-element is the
  bidirectional half — the orphan and dangling clauses and the non-vacuity condition
  constrain the justfile and the whole of `docs/`, and they are what stops the
  arrangement from being deleted. The value of the freshness half is that it costs
  nothing to add the second surface.
- The check runs the generator, so the application gets composed more often. `just
  doc-freshness` measures at 1.7s against `tool-docs-check`'s 1.6s, and a CI leg
  reaches the walker three times — its own step, `verify` -> `static`, and `prek run
  --all-files` — plus a fourth inside the suite, where
  `test_passes_on_the_committed_repository` runs the whole thing end to end. Call it
  seven seconds added to each of eight legs, and it scales with the number of
  distinct regeneration commands: each one gets its own copy of the tracked tree and
  its own run. It is the price of executing rather than inspecting, and inspecting is
  what #480 rejected.
- **The check, and now part of the unit suite, need a prepared checkout.** The guard
  itself needs `git` and `just`; the recipe it runs needs `uv` and a populated
  `.venv`, and
  `test_passes_on_the_committed_repository` runs the real command, which is what
  makes it end-to-end. All of that is present after `just setup`, in CI and in a prek
  hook alike. A bare `python scripts/check_generated_docs.py` in an unprepared
  checkout fails on the subprocess rather than passing vacuously.
- **This ADR does not subsume #510.** Decision records are class 1b — they are
  judgement, not generated — so they carry no banner and the walker does not reach
  them. #510's property (a record's H1 number must match its filename number) is a
  content check on a prose document and belongs in
  `scripts/check_adr_numbering.py`, which is exactly where §1b says it goes.
- The presence assertions in `tests/test_ci_pipeline.py` are now, by §1c, recorded
  defects rather than accepted practice. Epic #475 owns replacing the rest of them.
  One went in the same change as this rule, because adding a `static` member would
  otherwise have meant hand-editing `config.count("pass_filenames: false") == 8` in a
  test about something else: `test_prek_hooks_delegate_to_focused_just_recipes` now
  parses `static`'s dependency list and the hook file's `entry: just <recipe>` lines
  and asserts the two are the same set, per hook rather than by whole-file count.
  What it still names by hand is `STATIC_GATES`, a floor: two files agreeing with
  each other is silent when a gate is deleted from both, and which gates this
  repository must not lose is a judgement no file states — §1b, not §1c. The
  correspondence is derived; the floor is a decision, and it is written where a
  decision belongs.
- **This change also adds three presence assertions of the kind §1c names.** The
  `doc-freshness` recipe name and body in `test_justfile_exposes_one_composed_
  verification_graph`, and `run: just doc-freshness` in the CI-step test, follow the
  pattern already there for every other recipe. The property they should state — that
  a named CI step invokes a defined recipe — is derivable, and epic #475 owns it. They
  are recorded here rather than left for someone to find, since a record establishing
  §1c should say where it did not yet apply it.

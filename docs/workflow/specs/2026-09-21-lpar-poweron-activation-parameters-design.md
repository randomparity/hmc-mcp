# LPAR PowerOn activation parameters

Issue #867, under epic #866. Decision record: [ADR 0161](../../adr/0161-lpar-poweron-activation-parameters.md).

## Problem

`power_on_lpar_job()` (`src/hmc_mcp/jobs/requests.py:61-66`) takes no arguments and
emits `force=false`, `novsi=true`, `bootmode=norm`. A partition therefore cannot be
activated to SMS or Open Firmware, and cannot be activated against a named partition
profile, from any surface this package offers. `LogicalPartitionProfile` and
`OperationType` are documented and never sent.

## Scope

Three optional job parameters become reachable from the builder up to the MCP tool
and the CLI.

- `src/hmc_mcp/jobs/requests.py` — `BootMode = Literal["norm","dd","ds","of","sms"]`
  and `PowerOnOperationType = Literal["activate"]` with matching `frozenset`s, beside
  the `RemoteRestartOperation` pattern at `:15-18`;
  `power_on_lpar_job(profile_uuid=None, bootmode="norm", operation_type=None)`
  validates membership, then emits `force`, `novsi`, `bootmode` in today's order and
  appends `LogicalPartitionProfile` and `OperationType` only when supplied.
- `src/hmc_mcp/jobs/__init__.py` — re-export the four new names into the existing
  aggregation. The module defines no `__all__` and must not gain one
  (`tests/unit/test_public_api.py:65`).
- `src/hmc_mcp/operations/lpar/core.py` — `power_lpar` (`:433`) and `power_on_lpar`
  (`:227`) gain keyword-only `boot_mode`, `partition_profile_uuid`, `operation_type`
  and pass them to the builder on the PowerOn arm only. The PowerOff arm and ADR
  0158's `_LPAR_POWER_OPERATIONS` guard (`:497-500`) are untouched.
- `src/hmc_mcp/server_tools/lpar/lifecycle.py` — `hmc_power_on_lpar` (`:314`) gains
  the same three, typed with the `Literal` aliases so the tool schema carries an
  enum. Each gains an `Args:` entry, which is the source of the rendered MCP schema
  description. Its **first** docstring line gains the partition-profile distinction,
  because that line is the only thing `docs/tools/` publishes.
- `src/hmc_mcp/cli_commands/lpar/lifecycle.py` — `lpars_power_on` (`:13`) gains
  `--boot-mode`, `--partition-profile`, `--operation-type`, threaded through
  `_power_lpar` (`:87`). `lpars_power_off` is untouched.
- `docs/capabilities/operations.json` — the `signature` field of the
  `hmc_power_on_lpar` record, and nothing else. It stores
  `str(inspect.signature(handler))`, which `scripts/check_capability_inventory.py`
  compares by string equality inside `just verify` and the `capability-inventory`
  hook, so changing the tool's parameters makes it stale.
- `docs/tools/lpar.md` — regenerated by `just tool-docs`.

**Ownership.** Each surface keeps the responsibility it already has: the builder
owns the wire vocabulary and its refusal, the operations layer owns power policy,
the tool and CLI own presentation. No transition is needed and no caller migrates:
every new parameter is optional, so `power_lpar`'s three existing callers
(`operations/lpar/provision.py:285`, `server_tools/lpar/lifecycle.py:411`,
`cli_commands/lpar/lifecycle.py:109`) and `power_on_lpar`'s one
(`server_tools/lpar/lifecycle.py:358`) keep today's behaviour untouched.

**Not in scope** (owners in the issue's `WORK:SCOPE` annotation): `OperationType=netboot`
and its parameter family (#868); `keylock` and `changeKeylock`; profile
name-to-UUID resolution; an `lpar_netboot` wrapper; IBM i network-installation
parameters; live-HMC verification.

### Failure model

**Actors and deployments.** A local operator at a terminal running `hmc-mcp lpars
power-on`; an LLM client calling `hmc_power_on_lpar` over MCP stdio; a Python caller
importing `hmc_mcp.operations.lpar.core`; and, inside the package,
`operations/lpar/provision.py:285`, which activates a partition it has just created.
All four already reach `power_lpar` and already submit PowerOn jobs. Provision is the
one that meets the freshly-created-partition case the second accepted class below
names; it passes no new argument, so it keeps today's document.

**Invariants and assets at stake.**

- The emitted job document for a call passing no new argument is byte-identical to
  today's — the epic's stated compatibility promise.
- Only the five documented boot modes and the one documented operation type reach
  the wire.
- `partition_profile_uuid` is caller-supplied text that lands inside XML, so it is an
  injection surface.
- PowerOn changes the state of a real partition; the ADR 0011 ownership path and the
  already-running check are unchanged by this work.

**Accepted failure classes.**

- A caller passing a profile UUID that does not exist, or a profile the partition
  cannot use, gets the HMC's own job error. This package does no pre-flight
  existence check — no profile feed read exists (ADR 0161), and inventing one is
  excluded.
- `bootmode=sms` and `of` are unverified against hardware; the document shape is
  what this change proves. Held by the issue's `verification:live-hmc` label.
- Whether a freshly created partition needs `LogicalPartitionProfile` to activate is
  unverified here; the issue records it as an unreproduced CLI-path report.
- A boot mode the HMC rejects for a given partition type — IBM i, for instance — is
  refused by the HMC, not by this package. The reference scopes `bootmode` to AIX,
  Linux and VIOS partitions and defines no closed per-type mapping to encode.

**Covered elsewhere.** XML escaping of every string argument is held by
`@escapes_string_arguments` on `build_job_request` (`src/hmc_mcp/xmlutil.py`), proved
by the generated cases in `tests/unit/test_xml_escaping.py`. Partition-state
vocabulary is held by `src/hmc_mcp/operations/partition_state.py`. The `/do/{operation}`
path segment is held by ADR 0158.

### Threat model

The change builds an XML document from non-literal values, so the trigger fires even
though no authn, authz, tenancy, secret, permission grant, dependency, or security
default is touched.

**Boundaries.** Added: none. Widened: three — the `hmc_power_on_lpar` tool call, the
`lpars power-on` command line, and the `power_lpar`/`power_on_lpar` Python calls each
accept three more caller-controlled values that reach the PowerOn job document. The
document's existing encoding boundary (`build_job_request`) and the HTTPS boundary to
the HMC are unchanged.

**Actors.** An LLM client driving the MCP tool is the untrusted party: its arguments
originate in a conversation this package does not control. The local operator and the
Python caller are trusted to the extent they already are — they can submit a PowerOn
job today. The HMC itself is trusted and authenticated by the existing session.

**Control per boundary.** `boot_mode` and `operation_type` are refused by
`frozenset` membership in `power_on_lpar_job` before any XML is built, so a
non-member never reaches the document; the `ValueError` names the permitted set and
not the rejected value, matching ADR 0158. `partition_profile_uuid` is not
validated for shape — the package has no profile feed to check it against — and is
carried on the existing escaped path: `@escapes_string_arguments` on
`build_job_request` escapes every string argument before formatting, which
`tests/unit/test_xml_escaping.py` proves by generated case for each string-carrying
builder parameter. A malformed UUID therefore reaches the HMC as inert escaped text
and is refused there, by the job.

**Out of scope.** Pre-flight existence or authorization checks on the supplied
profile UUID — accepted above, owned by the epic's excluded name-resolution work.
Rate limiting or auditing of PowerOn submissions — unchanged by this work and held
by the existing ADR 0011 ownership path and ADR 0092 §4 opt-in.

## Success

1. `power_on_lpar_job()` with no arguments returns a string equal, character for
   character, to the document on `main`.
2. `power_on_lpar_job` emits `LogicalPartitionProfile` exactly when `profile_uuid` is
   a non-empty string — `None` and `""` both mean omit, and neither is validated,
   because the profile has no vocabulary to check against. It emits `OperationType`
   exactly when `operation_type` is not `None`; `None` means omit, and every other
   value including `""` is validated against `POWER_ON_OPERATION_TYPES` and refused if
   it is not a member. `bootmode` is emitted on every call.
3. Each of the five members of `BOOT_MODES` and the one member of
   `POWER_ON_OPERATION_TYPES` is accepted. A `boot_mode` or `operation_type` value
   outside its `frozenset` raises `ValueError` naming that set sorted, before XML is
   built. No other parameter gains validation.
4. `power_lpar`, `power_on_lpar`, `hmc_power_on_lpar` and `hmc-mcp lpars power-on`
   each carry all three parameters, and the CLI's flags are `--boot-mode`,
   `--partition-profile`, `--operation-type`.
5. None of the three new parameters is named `profile` on any of those four surfaces.
   `hmc_power_on_lpar`'s docstring distinguishes the connection profile from the
   partition profile in two places: the `Args:` entries, which become the rendered MCP
   schema descriptions, and the first line, which is what `docs/tools/lpar.md`
   publishes. The second is how criterion 6's `docs/tools/` half is met;
   `scripts/gen_tool_reference.py` renders no parameter text and is not changed.
6. `just verify` and `uv run --no-sync prek run --all-files` are green, with
   `docs/tools/` regenerated and the `hmc_power_on_lpar` signature record in
   `docs/capabilities/operations.json` updated.

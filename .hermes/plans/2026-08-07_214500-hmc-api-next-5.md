# HMC API Surface: Next 5 Feature Commits

**Goal:** Implement 5 remaining high-value HMC REST API capabilities, each as
its own commit, in order: (1) Live Partition Mobility, (2) Virtual Network
management, (3) Template Library deploy, (4) system/VIOS power jobs,
(5) Virtual Media Repository.

**Architecture:** Extend the existing `hmc-mcp` package. Each item follows the
established pattern: XML/job builders in `templates.py`/`jobs.py`, async client
methods in `client.py`, `@mcp.tool` wrappers in `server.py`, Typer commands in
`cli.py`, and respx-mocked tests in `tests/`. One commit per item.

**Tech Stack:** Python 3.12, FastMCP, Typer, httpx (async), defusedxml,
pydantic-settings; tests via pytest + pytest-asyncio + respx.

**Repo:** `~/src/hmc-mcp` (local git, branch `master`, author David Christensen).
**Verification per item:** `uv run pytest -q` (all pass), `uv run python
scripts/smoke_mcp.py` (tool count grows), `uv run hmc-mcp <group> --help` (renders).

> **For Hermes:** implement item-by-item; commit after each; do not batch items
> into one commit. Use the existing code style (see `templates.py`, `client.py`).

## Established patterns to reuse (do not reinvent)

- **uom child CRUD**: `client.create_child(parent_type, parent_uuid, child_type, xml)`,
  `list_child(...)`, `delete_child(...)` → POST/GET/DELETE
  `/rest/api/uom/{Parent}/{uuid}/{ChildType}[/{child_uuid}]`.
- **uom list/get**: `client.list_uom(type)`, `get_uom(type, uuid)`,
  `get_uom_path(path, type)` → parse Atom feed via `parse_feed`.
- **Jobs**: `jobs.build_job_request(operation, group, parameters)` produces the
  JobRequest XML; `client.submit_job(full_path, xml)` POSTs it and returns the
  Job dict (poll with `get_job`). Job path form:
  `/rest/api/uom/{Parent}/{uuid}/do/{Operation}`.
- **Doc builders**: functions in `templates.py` return full XML strings with
  `UOM_NS`, `schemaVersion="V1_8_0"`, `<Metadata><Atom/></Metadata>`.
- **MCP tool shape**: thin sync wrapper calling `client_from_env()` + `_run()`.
- **CLI shape**: `*_app.command(...)` + `_run()` + `_fail()` + `Table`/`_print_json`.
- **Tests**: `respx` mock via the `mock_hmc` fixture; assert on
  `route.calls.last.request.content` (NOT `mock_hmc.calls.last` — that's the
  logoff DELETE after context exit).

## Item 1 — Live Partition Mobility (LPM)

**Objective:** Migrate/validate/abort/recover/remote-restart an LPAR between
managed systems.

**Spec (verified in cached PDF):** jobs on
`/rest/api/uom/LogicalPartition/{uuid}/do/{Op}` where Op ∈
`Migrate`, `MigrateValidate`, `MigrateAbort`, `MigrateRecover`, `RemoteRestart`.
Group = `LogicalPartition`. Key params (Migrate/MigrateValidate):
`TargetManagedSystemName`, `TargetProfileName`, `DestinationLparID`,
`SharedProcPoolID`, `WaitTime`. RemoteRestart also has a ManagedSystem-prefixed
path form; use the LogicalPartition form. MigrateValidate takes the same params
as Migrate. MigrateAbort/MigrateRecover take no params.

**Files:**
- Modify: `src/hmc_mcp/jobs.py` — add `migrate_lpar_job(target_system, **opts)`,
  `migrate_validate_lpar_job(target_system, **opts)`, `migrate_abort_lpar_job()`,
  `migrate_recover_lpar_job()`, `remote_restart_lpar_job(target_system)`. All via
  `build_job_request("Migrate", "LogicalPartition", params)` etc.
- Modify: `src/hmc_mcp/client.py` — add `lpar_migrate(lpar_uuid, target_system, **opts)`,
  `lpar_migrate_validate(...)`, `lpar_migrate_abort(lpar_uuid)`,
  `lpar_migrate_recover(lpar_uuid)`, `lpar_remote_restart(lpar_uuid, target_system)`.
  Each builds the job XML and calls `submit_job(f"/rest/api/uom/LogicalPartition/{lpar_uuid}/do/{Op}", xml)`.
- Modify: `src/hmc_mcp/server.py` — tools `hmc_migrate_lpar`,
  `hmc_migrate_validate_lpar`, `hmc_migrate_abort_lpar`, `hmc_migrate_recover_lpar`,
  `hmc_remote_restart_lpar`.
- Modify: `src/hmc_mcp/cli.py` — under `lpars_app`: `migrate`, `migrate-validate`,
  `migrate-abort`, `migrate-recover`, `remote-restart`. Resolve name→UUID via the
  existing `_resolve_uuid` helper; confirm destructive ops.
- Test: `tests/test_lpm.py` — job XML contains operation + `TargetManagedSystemName`;
  client posts to correct `do/` path; returns Job dict.

**Verify:** `uv run pytest -q` (expect 58 + new passing); smoke tool count = 38;
`uv run hmc-mcp lpars migrate --help` renders.

**Commit:** `feat: add Live Partition Mobility (migrate/validate/abort/recover/remote-restart)`

## Item 2 — Virtual Network management

**Objective:** List/create/delete Virtual Networks (VLANs) and list Virtual
Switches / Network Bridges so `adapters add-network` is self-contained.

**Spec:** VirtualSwitch is a ManagedSystem child:
`GET /rest/api/uom/ManagedSystem/{sys_uuid}/VirtualSwitch`. VirtualNetwork is a
top-level uom resource (`/rest/api/uom/VirtualNetwork[/{uuid}]`, GET/PUT/POST/
DELETE) with fields `NetworkName`, `NetworkVLANID`, `VswitchID` (or
`VirtualSwitchID`), plus `NetworkBridge` reference. NetworkBridge is a uom
resource. Exact child element names for VirtualNetwork create are less
consistent across docs — see Open Question below; fall back to generic if unsure.

**Files:**
- Modify: `src/hmc_mcp/templates.py` — `build_virtual_network_document(name, vlan_id, vswitch_id, switch_mode="VEB")`.
- Modify: `src/hmc_mcp/client.py` — `list_virtual_switches(system_uuid)` (child of
  ManagedSystem), `list_virtual_networks()`, `get_virtual_network(uuid)`,
  `create_virtual_network(name, vlan_id, vswitch_id)` (PUT to
  `/rest/api/uom/VirtualNetwork`), `delete_virtual_network(uuid)`,
  `list_network_bridges(system_uuid=None)`.
- Modify: `src/hmc_mcp/server.py` — tools `hmc_list_virtual_switches`,
  `hmc_list_virtual_networks`, `hmc_create_virtual_network`,
  `hmc_delete_virtual_network`, `hmc_list_network_bridges`.
- Modify: `src/hmc_mcp/cli.py` — new `network_app` ("network"): `list-switches`,
  `list-networks`, `create` (name/vlan/vswitch), `delete`, `list-bridges`.
- Test: `tests/test_network.py` — template field names; client PUT/DELETE paths;
  list parsing.

**Open question (resolve before coding):** confirm the exact VirtualNetwork
create element names (`VswitchID` vs `VirtualSwitchID`, and whether the create
is a top-level PUT or a ManagedSystem child PUT) against the reference client
(`/tmp/hmc_ref` if still present) or the PDF's Virtual Network section. If
ambiguous, implement `list_virtual_switches`/`list_virtual_networks`/
`list_network_bridges` (read) solidly and gate `create`/`delete` behind the
generic `raw` path until confirmed on a live HMC.

**Verify:** standard trio; smoke tool count = 43.

**Commit:** `feat: add virtual network management (switches, networks/VLANs, bridges)`

## Item 3 — Template Library deploy

**Objective:** Query partition templates and deploy a partition from one.

**Spec (verified):** templates live under `/rest/api/templates/` (note: NOT
`/uom/`). Partition templates: `GET /rest/api/templates/PartitionTemplate[/{uuid}]`.
Jobs: `POST /rest/api/templates/PartitionTemplate/{uuid}/do/capture`,
`/do/check`, `/do/transform`, `/do/deploy`. Deploy params: `TargetUuid`
(managed system), `TemplateUuid` (the *draft* template UUID — a
transform/replica), `K_X_API_SESSION_MEMENTO`. The normal flow is
capture→check→transform→deploy; deploy operates on a *draft* UUID, so full
deploy is multi-step. Media type: `application/vnd.ibm.powervm.templates+xml`.

**Files:**
- Modify: `src/hmc_mcp/jobs.py` — `partition_template_deploy_job(target_system_uuid, draft_template_uuid, memento)`
  and thin builders for `check`/`transform` via `build_job_request` (group `PartitionTemplate`).
- Modify: `src/hmc_mcp/client.py` — note the different base path + media type;
  add `list_partition_templates()`, `get_partition_template(uuid)` (GET
  `/rest/api/templates/PartitionTemplate...`, media type templates+xml), and
  `deploy_partition_template(draft_uuid, target_system_uuid)` (POST do/deploy).
  May need a `_templates_headers()` helper since base path/media differ from uom.
- Modify: `src/hmc_mcp/server.py` — tools `hmc_list_partition_templates`,
  `hmc_get_partition_template`, `hmc_deploy_partition_template`.
- Modify: `src/hmc_mcp/cli.py` — new `templates_app` ("templates"): `list`,
  `show`, `deploy`.
- Test: `tests/test_templates_api.py` — correct `/rest/api/templates/` path,
  deploy job params (`TargetUuid`, `TemplateUuid`), templates+xml media type.

**Risk:** the capture→transform→deploy chain is genuinely multi-step and
session-memento-dependent. Scope this item to **list + get + deploy-from-an-
existing-draft**; document that producing a draft (capture/transform) is a
follow-up. Don't over-build the full pipeline.

**Verify:** standard trio; smoke tool count = 46.

**Commit:** `feat: add template library query + partition deploy`

## Item 5 — Virtual Media Repository

**Objective:** Manage the VIOS media library (ISOs) so partitions can boot
install media.

**Spec:** Media Repository / Virtual Optical Media are operations on a
VolumeGroup POST (the only repository lives in a VG, always named `VMLibrary`).
Operations: Create/Delete Media Repository, Change repository size,
Create/Delete Virtual Optical Media (blank only). No standalone uom resource —
goes through `POST /rest/api/uom/VirtualIOServer/{vios}/VolumeGroup/{vg}` with
a `MediaRepositories`/`VirtualOpticalMedia` block. Exact element names should be
confirmed against the PDF's Virtual Media Repository / Virtual Optical Media
sections before coding.

**Files:**
- Modify: `src/hmc_mcp/templates.py` — `build_media_repository_document(size_mb)`,
  `build_virtual_optical_media_document(media_name, size_mb)` (VolumeGroup docs
  carrying the relevant block).
- Modify: `src/hmc_mcp/client.py` — `create_media_repository(vios_uuid, vg_uuid, size_mb)`,
  `create_virtual_optical_media(vios_uuid, vg_uuid, media_name, size_mb)`,
  `list_media_repository(vios_uuid, vg_uuid)` (parse from VG detail),
  `delete_virtual_optical_media(...)`. All POST to the VG path.
- Modify: `src/hmc_mcp/server.py` — tools `hmc_create_media_repository`,
  `hmc_create_virtual_optical_media`, `hmc_list_media_repository`,
  `hmc_delete_virtual_optical_media`.
- Modify: `src/hmc_mcp/cli.py` — under `storage_app`: `create-repo`,
  `create-media`, `list-repo`, `delete-media`.
- Test: `tests/test_media.py` — template block names; POST targets VG path.

**Open question (resolve before coding):** confirm the exact

## Order & dependencies

1. **LPM** — self-contained (jobs only), high value.
2. **Virtual Network** — read parts depend only on existing helpers; write part
   has an open question to resolve first.
3. **Template deploy** — different base path/media type; scoped to
   list/get/deploy-from-draft.
4. **System/VIOS power** — trivial; reuses existing job builders.
5. **Media repository** — depends on VG plumbing from prior work; least-documented
   element names.

No hard inter-item dependencies; they can be built in this order independently.
